# Documentation Standard: มาตรฐานเอกสาร

> Sprint 5 — CloudForge Platform Foundation
> สถานะ: Draft สำหรับ review
> เอกสารนี้กำหนดว่าเอกสารทุกไฟล์ในแพลตฟอร์ม (รวมถึงไฟล์นี้เอง) ต้องเขียนและจัดเก็บอย่างไร
> ใช้เป็น reference เมื่อสร้างเอกสารใหม่ทุกครั้งตั้งแต่ Sprint 5 เป็นต้นไป

---

## 1. เป้าหมายและขอบเขต

เอกสารของแพลตฟอร์มเริ่มมีจำนวนมาก (7 ไฟล์ Sprint 1-3 + 2 ไฟล์ Sprint 4 + ไฟล์นี้)
และจะเพิ่มขึ้นเรื่อยๆ ทั้ง ADR, agent metadata, และเอกสารเฉพาะแอป — ถ้าไม่มีมาตรฐานกลาง
แต่ละไฟล์จะเขียนไม่เหมือนกัน ทำให้อ่านยากและเชื่อมโยงกันไม่ได้

เอกสารนี้กำหนด: โครงสร้างไฟล์, header มาตรฐาน, การใช้สถานะ (status badge), กฎการอ้างอิง
ข้ามเอกสาร, ภาษาที่ใช้, และ process การทบทวน/อัปเดตเอกสาร
ไม่ครอบคลุม: เนื้อหาเฉพาะทาง technical ของแต่ละเอกสาร (นั่นคือหน้าที่ของเอกสารนั้นๆ เอง)

## 2. โครงสร้างโฟลเดอร์ (ยึดตามที่มีอยู่แล้ว) กฎ: ไฟล์ใหม่ต้องอยู่ในโฟลเดอร์ที่ตรงกับหน้าที่ที่สุด ถ้าไม่แน่ใจว่าควรอยู่โฟลเดอร์ไหน
ให้เปิดเป็นคำถามใน Open Items ของไฟล์นั้น แทนที่จะสร้างโฟลเดอร์ใหม่เอง

## 3. Header มาตรฐาน (บังคับทุกไฟล์)

ทุกเอกสารต้องขึ้นต้นด้วย blockquote header 3 บรรทัดนี้เสมอ ก่อนเนื้อหาจริง:

```markdown
# ชื่อเรื่อง

> Sprint ที่สร้าง/แก้ล่าสุด — CloudForge Platform Foundation
> สถานะ: Draft / Under Review / Approved
> ความสัมพันธ์กับเอกสารอื่น (ถ้ามี) เช่น "เอกสารนี้เชื่อมกับ X.md"
```

เหตุผล: ผู้อ่านที่เปิดไฟล์ใดไฟล์หนึ่งแยกจากบริบทเดิม ต้องรู้ทันทีว่าไฟล์นี้อยู่ Sprint ไหน
สถานะเป็นอย่างไร และควรอ่านคู่กับไฟล์ไหนบ้าง

## 4. Status Badge มาตรฐาน

ใช้สัญลักษณ์เดียวกันทุกเอกสารเพื่อสื่อสถานะงาน ห้ามใช้คำอื่นแทน (เช่น "เสร็จแล้ว" เฉยๆ
โดยไม่มีสัญลักษณ์) เพื่อให้ scan สถานะข้ามเอกสารได้เร็ว:

| สัญลักษณ์ | ความหมาย |
|---|---|
| 🟢 | เสร็จแล้ว / ผ่านแล้ว / ปลอดภัยแล้ว |
| 🟡 | ทำบางส่วน / มีเงื่อนไข / ต้องระวัง |
| 🔴 | ยังไม่ได้ทำ / มีความเสี่ยง / ยังไม่แก้ |
| ⚪ | ยังไม่เริ่ม / อยู่ในขั้นแนวคิด |

## 5. กฎการอ้างอิงข้ามเอกสาร

- เมื่ออ้างถึงเอกสารอื่น ให้ใช้ชื่อไฟล์ใน backtick เสมอ เช่น `SECURITY_MODEL.md`
  ไม่ใช่พิมพ์ชื่อเรื่องแบบอิสระ (ป้องกันความสับสนเมื่อค้นหา)
- ถ้าอ้างถึงหัวข้อย่อยในเอกสารอื่น ให้ระบุเลขข้อด้วย เช่น `SECURITY_MODEL.md ข้อ 10`
  เพื่อให้ผู้อ่านเจอจุดที่อ้างถึงได้เร็วโดยไม่ต้องอ่านทั้งไฟล์
- ห้ามคัดลอกเนื้อหาจากเอกสารอื่นมาวางซ้ำ — ให้อ้างอิง (reference) แทนเสมอ เพื่อไม่ให้
  เนื้อหาสองที่ไม่ตรงกันเมื่อมีการแก้ไขในอนาคต (single source of truth)

## 6. ภาษาที่ใช้

- เนื้อหาหลักเขียนเป็น**ภาษาไทย** เพื่อให้ทีมอ่านและสื่อสารกันได้เร็วที่สุด
- คำศัพท์ทาง technical ที่ไม่มีคำแปลไทยที่ชัดเจน หรือเป็นชื่อเฉพาะ (เช่น `Firestore`,
  `Zero Trust`, `least privilege`, ชื่อ field/endpoint) ให้คงเป็นภาษาอังกฤษ ไม่บังคับแปล
- ชื่อไฟล์ (`.md`) ใช้ภาษาอังกฤษตัวพิมพ์ใหญ่คั่นด้วย `_` เสมอ (`SECURITY_MODEL.md`
  ไม่ใช่ `security-model.md` หรือ `รูปแบบความปลอดภัย.md`) เพื่อความสม่ำเสมอกับไฟล์เดิม

## 7. Markdown Style Guide

- ใช้ `##` สำหรับหัวข้อหลัก, `###` สำหรับหัวข้อย่อย — ไม่ข้ามระดับ (ห้ามกระโดดจาก `#`
  ไป `###` ตรงๆ)
- ตารางใช้เมื่อเปรียบเทียบหลายรายการที่มีโครงสร้างเดียวกัน (เช่น status ของแต่ละแอป)
  ถ้าเป็นการอธิบายไหลลื่นแบบ narrative ให้ใช้ paragraph แทนการยัดใส่ตาราง
- Checklist (`- [ ]`) ใช้เฉพาะกับ Open Items / งานที่ยังไม่เสร็จเท่านั้น ไม่ใช้ปนกับ
  bullet list ทั่วไป
- Code block ระบุภาษาเสมอเมื่อเป็นโค้ดจริง (เช่น ```javascript```) แต่ diagram แบบ text
  ธรรมดาไม่ต้องระบุภาษา
- ทุกไฟล์ปิดท้ายด้วยหัวข้อ **"Open Items"** เป็นมาตรฐานเดียวกับที่ใช้ใน Sprint 1-4
  แม้ไม่มีอะไรค้างก็ให้เขียนว่า "ไม่มีรายการค้าง ณ ตอนนี้" แทนการละหัวข้อนี้ไปเฉยๆ

## 8. Review & Update Process

- เอกสารที่มีสถานะ `Draft` ต้องผ่าน review อย่างน้อย 1 รอบก่อนเปลี่ยนเป็น `Approved`
- เมื่อแก้เอกสารที่ `Approved` แล้วในจุดที่กระทบเนื้อหาสาระ (ไม่ใช่แค่ตัวสะกด) ต้องเปลี่ยน
  สถานะกลับเป็น `Under Review` ชั่วคราว และปรับ header ข้อ 3 ให้ระบุ Sprint ที่แก้ล่าสุด
- ADR ที่ตัดสินใจแล้วถือเป็น**ประวัติศาสตร์** ห้ามแก้ย้อนหลัง — ถ้าการตัดสินใจเปลี่ยน
  ให้เปิด ADR ใหม่ที่อ้างอิงว่า "supersedes ADR-00X" แทน (ดู `ADR_TEMPLATE.md` ที่จะสร้างคู่กับ
  ไฟล์นี้)
